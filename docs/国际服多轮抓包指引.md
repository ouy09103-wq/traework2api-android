# 抓包指引：国际服「发第二条消息」到底发了什么请求

> 目的：补上 `traework2api` 国际服**多轮上下文**的最后一块拼图。
> 背景与已排除的路见 `交接文档.md` §5.10。这份是**只做一件事**的操作清单。

---

## 为什么需要你抓（而不是 AI 自己试）

AI 在设备上只能**盲试字段**：试 `chat_session_id`（已试，上游忽略）、试 `content`（已试，直接不生成）。
真正破局的是**看 web 端自己怎么发的** —— 交接文档 §5.9.5 就是这么定下三段式协议的：
> 最初在 App 里加临时探测按钮穷举请求体……**真正破局的是浏览器抓包 —— 比盲试快得多。**

你抓一次包，我改一行 `createBody` 就能生效。所以请你出手。

---

## 要抓什么（一句话）

在 `work.trae.ai` 上**同一个对话里连发两条消息**，把**第二条**发出去时的请求抓下来。

第二条是关键：第一条是"建会话"，我们**已经会了**；要的是"**往已有会话里追加**"长什么样。

---

## 操作步骤

### 1. 打开开发者工具
- 电脑上用 **Chrome / Edge** 打开 `https://work.trae.ai`（用电脑浏览器，环境完整，比手机稳）
- 按 **F12** → 切到 **Network（网络）** 标签页

### 2. 先清空、再开录制
- 点 Network 面板左上角的 **🚫 清空** 图标（清掉已有记录，免得干扰）
- 勾上 **Preserve log（保留日志）** —— 这条很重要，页面跳转/SSE 长连接时不会丢记录
- 筛选框可以先留空（**不要**只筛 Fetch/XHR，SSE 可能被归类到别的类型）

### 3. 发第一条消息（这条我们已经有能力复现）
在对话框里发一句能让它记住信息的话，例如：

> 我叫小明，请只回复：好的

等它回完（回"好的"就行）。

### 4. 发第二条消息（**这才是要抓的**）
在**同一个对话里**接着发：

> 我叫什么名字？

等它答完。

### 5. 导出
我们要的是**第二条消息**触发的那几个请求。请把 Network 里从第二条消息开始出现的请求都看一下。

---

## 具体想要哪些信息

⚠️ **不要把 token / Authorization 头贴给我。** 那是账号凭据，交接文档 §6 是红线。
我只需要**请求的形状**。下面每一项都请**手工抄字段名和值**（值里如果含 token，用 `<你的token>` 代替）。

### A. 建/加消息的那个请求（最重要）

在第二条消息发出后，找 **`chat_sessions` 相关**的请求。大概率是下面两种之一：

| 情况 | 长什么样 | 我要抄什么 |
|---|---|---|
| **① 还是 POST `/chat_sessions`** | 跟第一条同一个端点 | 请求体**全文**（`chat_session_id` 字段是不是非空了？多了什么新字段？） |
| **② 换了个端点**（很可能是这个） | 例如 `POST /chat_sessions/{id}/messages`、`/reply`、`/turns`、`PATCH /chat_sessions/{id}` | **完整 URL 路径** + 请求体**全文** |

**请直接右键该请求 → Copy → Copy as cURL**，然后**手工把 `Authorization` / `X-*` token 头删掉/打码**再贴给我。这样字段形状一定不会抄错。

### B. 请求头里有没有新东西
第二条请求的头，和第一条比，**有没有多出来的**（比如 `reply_to_message_id`、
`last_message_id`、`parent_message_id`、`turn_id` 之类）？有就列出来。

### C. 响应
那条请求的**响应体**（通常是 JSON，含新的 `message_id`）。

### D. SSE 那条确认一下
第二条消息对应的 **`.../events?...`** 请求，它的 **query string 全文**是什么？
（特别看 `reply_to_message_id` 指向的是**第一条**还是**第二条**的 message_id —— 这可能就是关键。）

---

## 抄的时候注意（几个坑）

1. **别看错条数**：一定要确认抓的是**第二条**。第一条我们也已经会了，抄了没用。
2. **SSE 长连接**：`events` 那条是流式的，Network 里会一直挂着。点它 → **Response** 标签能看全文。
   如果 Response 是空的，切到 **EventStream** 标签页。
3. **同一条 `id` 会反复出现**：这是正常的（累积快照），不用管。
4. **别反复刷新登录**：GitHub OAuth 会限流（交接文档已记）。

## 交给我之后我会做什么

1. 对比第二条请求和第一条的差异，确定"追加消息"的正确形状；
2. 改 `TraeIntlUpstream.createBody()`（如果换了端点，就再加一个方法）——
   `sessionKey` / `sessions` / `rememberSession` 那套复用逻辑已经写好了，就等正确的字段名；
3. 在 `selfCheck()` 里把新形状钉住；
4. 用模拟器实测：第一轮说"我叫小明"，第二轮问"我叫什么"——**答出"小明"就算成**。

## 如果抓不到 / 太麻烦

也可以只回答我一个问题，往往就够定位了：

> **你在 web 上发第二条消息时，浏览器地址栏的 URL 变了吗？**
> （比如从 `work.trae.ai` 变成 `work.trae.ai/chat/<某个id>`）

如果变了，说明会话 id 是走 **URL 路径**的，那追加消息的端点八成是
`POST /chat_sessions/{id}/...` 而不是我们猜的那个 —— 这就已经排掉一半可能性了。
